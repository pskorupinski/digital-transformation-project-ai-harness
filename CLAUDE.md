# CLAUDE.md

Harness for **digital transformation projects**: turning a business's existing process into a
web solution, from discovery to a working vertical slice. Humans own discovery and every
decision; Claude structures, proposes and builds — always traceably.

## Process and file roles

| Step | Owner | Command | Reads | Writes |
|---|---|---|---|---|
| 01 Brief | human | — | — | `docs/01-brief.md` |
| 02 Features | Claude → human | `/02-features` | 01 | `docs/02-features.md`, brief §11 |
| 03 Architecture | Claude → human | `/03-architecture` | 01–02, decisions | `docs/03-architecture.md`, proposed decisions |
| 04 Spec | Claude → human | `/04-spec F-nn` | 01–03 | `docs/04-specs/F-nn-<slug>.feature` |
| 05 Build slice | Claude → human | `/05-build-slice F-nn` | 02–04, decisions | `backend/`, `frontend/`, status updates |

Three kinds of truth — keep them apart:

| Question | Lives in |
|---|---|
| **How** we work | this file |
| **What** we build | `docs/` |
| **Why** we chose it | `decisions.md` |

## Scope levels

| Scope | Meaning |
|---|---|
| `v0` | First working build — validates the solution with the business. Capabilities may be fake. |
| `v1` | First release to real customers — every capability real, plus what launch requires |
| `v2` | Next iteration after launch |
| `cut` | Not building; the reason is on the cut list |

A trailing `?` (`v0?`) marks a proposal. Only a human removes it.

## Traceability IDs

Every generated artifact cites its sources with these IDs. Missing information becomes a new
`A-nn` row in brief §11 — never a silent guess.

| ID | Refers to | Defined in |
|---|---|---|
| `§n` | Brief section | `docs/01-brief.md` |
| `A-nn` | Assumption or open question | brief §11 |
| `F-nn` | Feature | `docs/02-features.md` |
| `I-nn` | Capability (integration) | `docs/03-architecture.md` § Capability register |
| `F-nn/S-nn` | Scenario | `docs/04-specs/` |
| `D-nn` | Decision | `decisions.md` |

## Guardrails

1. **Stay in scope.** Build only features whose scope has no `?`. Never invent business facts.
2. **Architecture is a contract.** Follow `docs/03-architecture.md` and accepted decisions.
   If reality disagrees, stop and propose a change (a `proposed` row in `decisions.md`).
3. **No new dependencies without asking.** Pre-approved: `react-router` (when a slice needs a
   second page).
4. **Tests come from scenarios (D-04).** One test per Gherkin scenario, named `test_s01_<slug>`
   (backend) or `it('F-01/S-01 …')` (frontend). `tests/test_traceability.py` enforces it.
5. **Small steps, visible checkpoints.** Present the plan before coding. Commit code at each
   green checkpoint (`F-nn: <step>`). Docs are committed by the human after review
   (`Human: …`) — that commit is the approval; never commit them on their behalf. Never push.
6. **Generated migrations are reviewed.** Show every autogenerated Alembic script and flag
   drops, renames and type changes before applying it.
7. **No visual polish.** Brand (brief §5) lives only in `frontend/src/theme.css` tokens;
   components use tokens, never raw colours. Layout = plain semantic HTML.
8. **Hooks are the quality gate.** Lint/format runs after every edit; tests run before a turn
   ends. Don't bypass or silence them — fix the cause or explain why the failure is expected.
9. **Markdown must render.** Leave a blank line before every table, list and code block; use
   tables rather than `·`-joined runs for lists of items.

## Stack (D-02)

| Part | Technology |
|---|---|
| `backend/` | FastAPI, SQLAlchemy 2.0 typed models, Pydantic, Alembic, pytest, ruff |
| `frontend/` | React, Vite, TypeScript, vitest + Testing Library, oxlint |
| `docker-compose.yml` | Postgres 17 (`app`, `app_test`), backend :8000, frontend :5173 |

| Folder | Holds |
|---|---|
| `backend/app/models/` | ORM models — import each one in `app/models/__init__.py` |
| `backend/app/schemas/` | API contracts, separate from the ORM on purpose |
| `backend/app/services/` | Business logic; owns transactions |
| `backend/app/api/` | Thin routers calling services |
| `backend/app/integrations/` | Capability ports, fake adapters, `mock_providers.py` |
| `frontend/src/api/client.ts` | The only way the UI calls the API (relative `/api` path) |

The backend container mounts the repo read-only at `/repo` so the traceability test can read
`docs/` and the frontend tests.

## Capability pattern (D-01)

For each register row with v0 = `fake`: a `Protocol` port named after the capability (not a
vendor) that services depend on, a `Fake…Adapter` mirroring the contract shape, and a factory
choosing by `INTEGRATIONS_MODE`. If the real system calls back asynchronously, the fake
simulates it: a mock-provider route schedules a `BackgroundTask` that sends the event over
HTTP to **our real inbound route**.

## Commands

```bash
docker compose up --build -d                                   # start everything
docker compose exec backend pytest                             # backend tests + traceability
docker compose exec backend alembic revision --autogenerate -m "<msg>"
docker compose exec backend alembic upgrade head
docker compose exec backend python -m app.seed                # demo data, idempotent
docker compose exec frontend npm test                          # frontend tests
docker compose exec frontend npm run typecheck
docker compose logs -f backend                                 # debug
```
